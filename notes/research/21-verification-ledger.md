## 1. CONFIRMED

**Claim as originally stated**

> TypeDoc cannot be used for libtmux-ts today because TypeDoc's package.json declares peerDependencies.typescript "5.0.x || ... || 6.0.x" while libtmux-ts pins typescript 7.0.2, making @microsoft/api-extractor the only working TypeScript API-doc path.

**Corrected statement**

TypeDoc 0.28.20 declares peerDependencies.typescript = "5.0.x || 5.1.x || 5.2.x || 5.3.x || 5.4.x || 5.5.x || 5.6.x || 5.7.x || 5.8.x || 5.9.x || 6.0.x", and libtmux-ts pins typescript 7.0.2 (root and packages/libtmux). This peerDependency mismatch alone is only a soft warning in both bun's installer and TypeDoc's own code (application.ts logs via logger.warn, does not throw) — installing typedoc into libtmux-ts succeeds with just "warn: incorrect peer dependency". The real, harder blocker is structural: TypeScript 7.0.2 is the Go-native ("Corsa") compiler rewrite, and its package.json exports map the root import to lib/version.cjs, which contains only `version`/`versionMajorMinor` — the classic Compiler API (SyntaxKind, createProgram, etc.) is absent from the package entirely (zero matches for "SyntaxKind" anywhere under node_modules/typescript). As a result TypeDoc crashes unconditionally at ESM module-load time — even `typedoc --version` throws `TypeError: Cannot read properties of undefined (reading 'PropertyDeclaration')` at typedoc/dist/index.js:537 — regardless of entry points, config, or flags; this is not something a --skipTypeCheck-style flag or peer-dep override can work around. TypeDoc's maintainer confirms this is structural and open-ended: GitHub issue TypeStrong/TypeDoc#3098 ("TypeScript 7 (TS-Go) support", open) states "The TypeScript 7 API is a complete rewrite... TypeDoc heavily depends on some internal features in TypeScript 6 which are not present in the TypeScript 7 API," with no ETA (maintainer notes ~1-2 volunteer hours/week). By contrast, @microsoft/api-extractor@7.59.0 works today and was re-verified independently: it declares "dependencies": {"typescript": "5.9.3"} and "peerDependencies": null in its own package.json, bundling a compiler that never touches the project's typescript@7.0.2, because it parses only already-emitted .d.ts declaration files rather than compiling source. Running `bun run build` (using the project's own tsc/typescript@7.0.2) produced fresh packages/libtmux/dist/*.d.ts, and `api-extractor run --local` against that output printed "Analysis will use the bundled TypeScript version 5.9.3" and "API Extractor completed successfully" (exit 0), emitting a 936,568-byte index.api.json with only warnings (ae-missing-release-tag, ae-forgotten-export, ae-unresolved-link), no errors. Conclusion stands: @microsoft/api-extractor is the only working TypeScript API-doc path for libtmux-ts today, but the failure mode for TypeDoc is a hard, unconditional startup crash caused by TS 7's API rewrite, not merely an ignorable peerDependency range.

## 2. REFUTED

**Claim as originally stated**

> Claim B (cross-licensing + matrix-swift): swift-docc's static-hosting output "is a Vue SPA" that "fights the static-S3 constraint" and needs SPA-style CDN route rewriting — contradicting Claim A (cross-aws-cdn), which says `--transform-for-static-hosting` pre-bakes a real index.html per route so no SPA fallback/rewriting is needed.

**Corrected statement**

Claim A is correct and Claim B's routing conclusion is refuted by source, though Claim B's "it's a Vue SPA" premise is true in a different sense.

`StaticHostableTransformer.transform()` (Sources/DocCCommandLine/Transformers/StaticHostableTransformer.swift:58-79) walks every `data/**/*.json` file in the archive and, for each one, creates a same-path directory containing a literal `index.html` file (`fileManager.createFile(...)` at line 77). This means every documentation/tutorial route DocC knows about gets a real, individually-addressable S3 object at build time — `/documentation/libtmux/foo` maps to object key `documentation/libtmux/foo/index.html`. Nothing about serving these routes needs a CDN-level "catch-all miss → serve index.html" SPA fallback rule.

The content written to every one of those files is byte-identical (the same `Data` blob, computed once via `StaticHostableTransformer.indexHTMLData(in:with:fileManager:)` before the loop starts, StaticHostableTransformer.swift:50-79) unless the build passes `--experimental-transform-for-static-hosting-with-content`, in which case `FileWritingHTMLContentConsumer` writes genuinely distinct per-page HTML instead (ConvertAction.swift:340: "Don't transform for static hosting if the FileWritingHTMLContentConsumer will create per-page index.html files"). Either mechanism still produces one real file per route — the choice only affects whether the file's content is a duplicated app shell or real page content, not whether the route resolves to a physical object.

Claim B's "Vue SPA" characterization is true only in the client-rendering sense: swift-docc-render is a webpack-built Vue app (package.json: `"vue-router": "^3.5.2"`) whose router runs in `mode: 'history'` (src/setup-utils/SwiftDocCRenderRouter.js:28) and whose data comes from client-side `fetch()` calls against the per-route JSON (src/utils/data.js). That is a JS-required-to-render / crawlability concern, not a CDN-routing concern — vue-router's history mode normally forces a server-side "unmatched path → index.html" rewrite specifically because a typical SPA deploy ships only ONE index.html; DocC's static-hosting transform sidesteps that exact problem by pre-generating a real file at every route vue-router would ever navigate to, so hard-navigation to any documented route hits a real S3 object directly, never falling through to a 404.

The genuinely SPA-fallback code path — literally "serve index.html regardless of requested URL" (DefaultRequestHandler.swift:19-21) — exists only inside `docc preview`'s embedded NIO dev server, compiled in only under the `PREVIEW_SERVER` Swift trait (Package.swift:51: `.define("PREVIEW_SERVER", .when(platforms: NIOPlatforms, traits: [previewServerTrait]))`, guarding every file under `Sources/DocCCommandLine/PreviewServer/`). It is architecturally and compilation-unit separate from `docc convert --transform-for-static-hosting`; it never ships to a production static-hosting output and is irrelevant to what gets deployed to S3.

`--hosting-base-path` semantics (StaticHostableTransformer.swift:95-131): the base path gets a leading `/` added if missing and a trailing `/` stripped if present, then is substituted for the literal `{{BASE_PATH}}` token. That token lives in `<base href="{{BASE_PATH}}">` in swift-docc-render's app/index.html:14 (placeholder injected at swift-docc-render's own webpack build via bin/baseUrlPlaceholder.js, left unresolved specifically so `docc convert` can fill it in later) and in every absolute asset `<script src="{{BASE_PATH}}/js/...">` reference. At runtime, docc-render reads its own base path back out via `baseUrl = new URL(document.baseURI).pathname` (src/utils/theme-settings.js:20), which resolves against that `<base>` tag — so vue-router's `base: baseUrl` and every relative asset/data fetch are anchored correctly under a subpath like `/swift/v1.2.3/api` as long as the exact same string is passed to `--hosting-base-path` at build time and matches the real deployed S3/CloudFront prefix.

URL patterns that would 404 without ANY rewrite: any request for an extensionless route path without its trailing slash (e.g. `/swift/v1.2.3/api/documentation/libtmux/foo` instead of `.../foo/`) — because the object key on S3 is `.../foo/index.html`, not `.../foo`, and the REST-endpoint-with-OAC origin recommended elsewhere in this research does no automatic directory-index resolution (only the S3 website endpoint does, and that requires a public bucket incompatible with OAC). The fix needed is exactly the same generic "if URI ends in `/`, append `index.html`; if the last segment has no `.` in it, 301-redirect to add the trailing slash" CloudFront Function already designed for all eight languages in cross-aws-cdn.json — nothing DocC-specific, and no wildcard/catch-all SPA rewrite rule at all. Adding a "serve root index.html on any 404" rule for DocC would be actively wrong: it would mask genuinely missing/mistyped documentation URLs behind a 200 response instead of a real 404, with no compensating benefit since every legitimate route already resolves to a real object.

**How it was verified**

Read StaticHostableTransformer.swift in full (the actual --transform-for-static-hosting implementation) — confirmed it writes a real index.html file into a same-named directory for every JSON data file in the doccarchive, i.e. one physical S3 object per documentation route, not a single SPA-shell file. Cross-checked swift-docc-render's vue-router config (history mode, real route table with client-only wildcard fallback) and its base-path plumbing (webpack <base href> placeholder -> {{BASE_PATH}} token -> resolved by StaticHostableTransformer at convert time -> read back at runtime via document.baseURI) to confirm --hosting-base-path correctly anchors routing/assets under a subpath like /swift/v1.2.3/api without requiring any CDN-side URL rewriting beyond generic directory-index handling.

**Consequence for the design**

The CloudFront Function design should NOT special-case DocC with any SPA wildcard-fallback rule (e.g. "unmatched path → serve /swift/.../index.html"). DocC needs exactly the same generic viewer-request rewrite already designed for the other seven languages in cross-aws-cdn.json: append `/index.html` when the URI ends in `/`, and 301-redirect extensionless no-trailing-slash paths to add the slash. No DocC-specific routing logic, no additional CloudFront behavior, and no KVS entries are required for Swift beyond what every other language already needs. The one DocC-specific build-time (not CDN-time) requirement to keep enforced in CI is that `--hosting-base-path` must exactly equal the real deployed prefix (e.g. `swift/v1.2.3/api`, or `swift/stable/api` for the alias rebuild) every time the archive is built, since that string gets baked into every route's `<base href>` and every absolute asset/script reference — mismatches break asset and data-fetch URLs at runtime, not routing. Claim B's real, valid point — that DocC's default output is a client-rendered shell requiring JavaScript, hurting crawlability/no-JS support — remains a legitimate concern for the search/SEO design, but the fix for that is `--experimental-transform-for-static-hosting-with-content` (already in the project's planned Swift CI command per matrix-swift.json), not any CDN-level SPA routing change.

## 3. PARTIALLY-TRUE

**Claim as originally stated**

> (1) S3 now supports conditional writes (If-Match/If-None-Match) enabling CAS version manifests; (2) GitHub Actions has GA "concurrency: {group, queue: max}" as of May 2026; (3) CloudFront KeyValueStore exists and CloudFront Functions read it synchronously, with specific size limits; (4) Astro 7 ships a Rolldown-based build pipeline; (5) Starlight has no first-party versioning, starlight-versions is the only option.

**Corrected statement**

1. CONFIRMED. Amazon S3 conditional writes are GA (announced Aug 2024). `PutObject`/`CopyObject` accept `If-None-Match: *` (fails 412 if the key already exists) and `If-Match: <etag>` (fails 412 on mismatch), giving true compare-and-swap semantics for a version manifest object. Requires SigV4 signing; exposed via `aws s3api put-object`, not `aws s3 cp`/`sync`.

2. CONFIRMED — this is real, not a hallucination, despite looking implausible against pre-2026 knowledge. GitHub Actions concurrency groups gained an opt-in `queue: max` property, announced on the GitHub Changelog 2026-05-07 ("GitHub Actions concurrency groups now allow larger queues") and documented in the official "Control the concurrency of workflows and jobs" page. Default behavior (`queue: single`, the historical behavior) still allows only one pending run per group, canceled/replaced by the next arrival. `queue: max` raises that to up to 100 pending jobs/workflow runs per group, processed FIFO by wait-start time. It cannot be combined with `cancel-in-progress: true` (validation error). So `concurrency: {group: deploy, queue: max}` is a legitimate, documented way to serialize N deploys without dropping any of them — no external lock/CAS needed for that specific problem.

3. PARTIALLY-TRUE — the store and read path are real, but "synchronously" is imprecise. CloudFront KeyValueStore exists and CloudFront Functions (JS runtime 2.0) read it via `cf.kvs()` and `kvsHandle.get()/.exists()/.meta()`. AWS's own reference shows every one of those calls is Promise-based and used with `await` (e.g. `const value = await kvsHandle.get("key", {format:"string"})`) — it is async/await syntax, not a synchronous/blocking return. AWS explicitly warns against `Promise.all`/promise-combinator use (recommends sequential `await` in a loop instead) because CloudFront Functions have no real concurrency — practically single-threaded and edge-local (the runtime independently disallows network, filesystem, env-var and timer access), so there's no live network round-trip the way Lambda@Edge would need, but the API surface is still Promise-based, not a plain synchronous call. Confirmed size limits (AWS CloudFront quotas page): key ≤512 bytes, value ≤1 KB, individual KVS ≤5 MB total, batch update ≤50 keys or 3 MB payload (whichever hit first), ≤200 KVS per account, 1 KVS per function, ≤100 functions per KVS.

4. CONFIRMED, with one precision. Astro 7.0 shipped 2026-06-22 (official Astro blog, corroborated by local `~/study/typescript/astro` clone at v7.2.4). The Rolldown bundler arrives transitively: Astro 7 upgrades to Vite 8, and "Vite now ships Rolldown, a Rust-based bundler that replaces both esbuild and Rollup with a single, unified bundler" (10-30x faster than Rollup, same plugin API), yielding Astro's own claimed 15-61% faster builds. Astro 7 separately also got a Rust-rewritten `.astro` compiler and a Rust-powered Markdown/MDX pipeline — distinct from, but announced alongside, the Rolldown/Vite-8 change. So "Astro 7 ships a Rolldown-based build pipeline" is accurate in effect; more precisely, Astro 7's default bundler is Rolldown by way of its Vite 8 dependency, not an Astro-authored bundler.

5. CONFIRMED. Starlight core (checked at v0.41.7, local clone synced 2026-08-14) has zero native versioning: a full-text search of the 3,017-line `packages/starlight/CHANGELOG.md` for "versioning"/"version switcher"/"versioned" returns no matches, and the withastro/starlight GitHub discussion #957 ("Support for Versioned Docs") remains open and stale (last updated 2024-06-12, no RFC merged). `starlight-versions` (HiDeoo) is the only community option: 99 stars/11 forks, actively pushed as recently as 2026-08-26, but its own README still states verbatim "Starlight Versions is an opinionated plugin that is still in early development. Expect frequent updates and changes to the plugin as development continues." Separately, Astro's Content Layer API (the load-bearing argument for choosing Astro to ingest 8 languages' machine-readable doc JSON) has been stable since Astro 5 (Dec 2024), well before Astro 7, with a built-in `file()` loader for JSON/YAML/TOML plus custom-loader support — so that part of the Astro argument holds independently of the versioning gap.

**Consequence for the design**

(1) and (2) together mean the CI/CD design can drop any bespoke cross-repo locking scheme: S3 `--if-match`/`--if-none-match` gives real optimistic-concurrency-controlled writes to a shared manifest object, and GitHub's native `concurrency: {group, queue: max}` (up to 100 pending runs, FIFO) can serialize an aggregator job across the 8 port repos without silently dropping triggers the way the old single-pending-run behavior did — S3 CAS should be documented as the backstop for actors `queue: max` can't see (manual re-runs, other CI systems), not the primary mechanism. (3) means a CloudFront Function can still resolve `/stable/`→`/vX.Y.Z/` from a KeyValueStore entry with no origin round-trip, but the design doc's code sketches must show `await kvsHandle.get(...)` inside the function (already valid, since CloudFront Functions JS runtime 2.0 supports async/await for this specific API), not describe it as a plain synchronous call — and the 512B key / 1KB value / 5MB store caps rule out storing a full version manifest in KVS; it should hold only compact alias→target pointers, with the full manifest served as a regular cached object. (4) confirms Astro 7 (and therefore Starlight, which requires Astro 7 as of Starlight 0.41) gets meaningfully faster builds for free via Vite 8/Rolldown — worth calling out as a build-time win for a monorepo that will compile 8 languages × N versions × M locales, independent of the versioning gap. Chunking is confirmed alphabetical/lazy (docs: "indexes are chunked alphabetically... `pagefind.preload('s')` will likely load the index required for 'static'"), so a single-site search downloads only the runtime + 1-2 matching chunks + a handful of fragments, not the whole index.

**Merging does not shrink this cost — it multiplies the chunk-fetch and fragment-fetch legs by the number of merged bundles.** `mergeIndex` shares the WASM engine (`load_wasm: false` for every secondary instance — coupled_search.ts:875-886), so the ~164KB runtime is loaded once regardless of how many languages are merged. But `search()` still calls each instance's own `search()` in parallel (`Promise.all(this.instances.map(i => i.search(...)))`), each fetching its own matching chunk from its own basePath. Extrapolating the measured 108-page/28KB-chunk numbers to 8 language sites of similar order of magnitude: a merged first search costs roughly 164KB runtime (one-time, cached) + up to ~8×28KB≈224KB of index chunks (one per merged bundle, in parallel) + fragments only for the results actually rendered (~5.5KB each). This is well above the docs' own "under 300kB, usually ~100kB" figure, which describes ONE site's search, not N merged sites searched simultaneously — that per-site figure should not be quoted unqualified for the merged 8-language case. Rustdoc/Javadoc/dokka in particular tend to emit far more, denser pages per API surface than Sphinx's 108 hand-authored pages, so per-language chunk counts/sizes could run well above this Python baseline — the 8x extrapolation is order-of-magnitude, not a tight bound.

Two further merge caveats, both from Pagefind's own docs (multisite.md, "Merging multiple languages" section): (1) CORS headers are required on every merged bundle's origin/path since merging happens in-browser across fetches; (2) all merged indexes share the PRIMARY instance's WASM module, so its language/stemming rules apply to every merged language's search — irrelevant if all 8 ports' docs are English, but a real caveat once human-language (i18n) translations are layered on top of the 8 programming-language ports, since a translated bundle's segmentation/stemming would follow the primary's language, not its own.

`exclude_selectors` (CLI `--exclude-selectors`, env `PAGEFIND_EXCLUDE_SELECTORS`, config key `exclude_selectors` — pagefind/src/options.rs, docs/content/docs/config-options.md) is CONFIRMED real and lets you strip rustdoc's sidebar / Sphinx's nav chrome via CSS selector at index time with zero changes to the generators. This is the load-bearing gap: an "Astro shell" plan has never costed how the reference language's docs get built under it.

No Doxygen-XML→Astro bridge (doxybook2, moxygen, or equivalent) was found anywhere in the research corpus — building one is undiscovered, uncosted work.
- **Go**: gomarkdoc's Markdown output is empirically verified and *renderer-agnostic* — the matrix states it is "directly ingestible by myst-parser... or by an Astro content collection with zero custom loader." Go is not a Sphinx-specific win; it costs the same either way. No live Sphinx Go-domain exists (sphinxcontrib-golangdomain: last push 2017-12-24, still 0.2.0.dev0; its companion godocjson, hosted under the readthedocs org, archived 2019-09-30) — irrelevant, since the practical path needs no domain bridge at all.
- **TypeScript**: the claim is factually wrong about the pick. matrix-typescript.json's actual recommendation is `@microsoft/api-extractor`'s `.api.json` (empirically run against real libtmux-ts output), consumed by "a small custom page-generator (Astro if that's the eventual framework, or a Sphinx/MyST reader...)" — explicitly renderer-agnostic. sphinx-js is not the recommendation; it is flagged BLOCKED TODAY, and independently confirmed here: TypeDoc 0.28.20's `peerDependencies.typescript` caps at `6.0.x` while libtmux-ts's own `package.json` pins `"typescript": "7.0.2"` — a blocker that hits sphinx-js AND any TypeDoc-JSON-into-Astro path identically, since both shell out to the same TypeDoc binary.
- **.NET/C#**: DocFX `metadata --outputFormat ApiPage` produces documented, versioned, pre-resolved-cross-reference YAML, and the matrix's recommendation explicitly targets "a custom Astro renderer." This is the one language genuinely recommended into Astro over Sphinx (though DocFX also has an untested `--outputFormat Markdown` that could plausibly feed myst-parser — not spiked, fidelity unverified).
- **Rust**: no clean tier1 path exists for EITHER shell. sphinxcontrib-rust would be the ideal Sphinx-native fit but is GPL-3.0-or-later end to end (both the Python extension and its bundled Rust parser binary, confirmed in both LICENSE/setup.py and Cargo.toml) — excluded on licensing grounds regardless of shell. rustdoc's JSON output requires `-Z unstable-options` on nightly (confirmed: fatal on stable, config.rs, tested locally on rustc 1.98.0 stable); `rustdoc-types` is a Rust-only crate with no official TS/JS port found, so an Astro consumer needs a hand-written adapter that doesn't exist yet. Both architectures require new code here; neither is a "just point the tool" story.
- **Java/Kotlin** and **Swift** sit outside the dichotomy entirely: both are tier2-skin-inject under Sphinx AND under Astro. Dokka's own Kotlin HtmlRenderer fills one opaque `<@content/>` template slot no framework can replace; its Markdown output (plugin-gfm) is self-reported ALPHA with search/style/nav preprocessors stripped out, confirmed in source. DocC/docc-render has no `<head>` injection flag at all (header/footer only insert into `<body>`) and forking swift-docc-render's compiled Vue dist (`DOCC_HTML_DIR`) is the only reskinning path, against an upstream committing "multiple times a week." DocC's RenderNode/RenderIndex JSON is real and stable (schema v0.4.2) but the matrix calls a from-scratch renderer on it "aspirational... a materially larger, separately-scoped investment." No maintained Sphinx bridge exists for either: javasphinx (Java) archived 2019-03-07, never added Kotlin; anarchy_sphinx (Swift's swift_domain) last pushed 2017-08-05.

A shell-independent cost the ledger surfaced and the original claim omits entirely: search-index suppression. Dokka writes `scripts/pages.json` with no disable flag (must hide `#searchBar` via CSS); DocFX needs its `ExtractSearchIndex` postprocessor omitted plus `_enableSearch:false`; TypeDoc's lunr index only suppresses via a non-`DefaultTheme` subclass; DocC ships an empty-shell SPA that is a Pagefind dead zone unless `--experimental-transform-for-static-hosting-with-content` is passed. This tax applies to at least 4 of 8 tools regardless of which shell wins.

Net: of 8 languages, only Python is a pure Sphinx case (by inheritance, uncontested since Astro was never costed for it); only .NET is a pure Astro case (explicitly recommended, prototyped); C++ and Go are cheap either way (Go strictly renderer-agnostic); TypeScript's actual recommendation is already renderer-agnostic; Rust has no clean off-the-shelf path in either architecture; Java/Kotlin and Swift are tier2-skin-inject regardless of the shell decision. The "two architectures in tension" framing is real for 1-2 languages (.NET vs. a hypothetical Sphinx path never attempted) but false as a description of the other 6.

**Consequence for the design**

The design doc should drop the "Sphinx camp vs. Astro camp" framing entirely and instead present the tier-by-language table above. Concretely: (1) Do not treat "pick Astro Starlight as shell" as free for Python — costing a from-scratch Astro renderer for Python's API docs (replacing autodoc/napoleon/intersphinx/doctest and the live libtmux.git-pull.com site) is a missing, likely large, work item that must be added to the SSG bake-off before a shell decision is final, or Python must be explicitly carved out as staying on Sphinx forever (making this a hybrid by definition, not a resolved single-architecture site). (2) TypeScript and Go are not evidence for either side — both recommendations are already renderer-agnostic (api-extractor JSON, gomarkdoc Markdown), so whichever shell wins costs the same for these two. (3) Java/Kotlin and Swift are permanently tier2 regardless of the shell decision — budget CSS/JS/head-footer injection work for them no matter what, and do not expect a shell choice to unify their page markup with the rest of the site. (4) Rust needs a licensing-and-toolchain decision independent of the shell question: either accept GPL contamination risk (sphinxcontrib-rust) or invest in a from-scratch nightly-rustdoc-JSON pipeline with a new Rust-to-{Astro-JSON|Sphinx-domain} adapter that doesn't exist today in either direction. (5) Budget a cross-cutting "search suppression" workstream (Dokka pages.json, DocFX ExtractSearchIndex, TypeDoc lunr guard, DocC static-hosting-with-content flag) as shell-independent engineering cost, not something a shell decision resolves. (6) The "thin shell owns only /, /concepts/, /parity/" hybrid the task asked about is closer to what the evidence actually supports than either pure-Sphinx or pure-Astro: Python/C++/Go can render natively wherever myst-parser or an Astro loader already exists cheaply; TS/.NET need one custom renderer either way; Java/Kotlin/Swift need tier2 skin-injection regardless; only the thin shell plus per-language tier assignment matches the ledger.
